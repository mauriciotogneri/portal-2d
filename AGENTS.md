## Project

Portal 2D — a desktop-only, keyboard-driven puzzle game: the player crosses grid-based test chambers using a pair of portals (Vite + Vue 3, TypeScript, Composition API with `<script setup>`, vue-router, ESLint + @stylistic + type-aware typescript-eslint via @vue/eslint-config-typescript). It is a static site on Firebase Hosting; there is no backend.

`todo/` holds the author's roadmap: one file per stage (`creator_platform.md`; stages 00, 01, 03, 04a and the campaign are done, stage 02 stopped after its prototype, and their files are removed; what stage 02 learned is in `docs/solver.md`, and the campaign's decisions and its workflow for each chamber are in `docs/campaign.md`). `creator_platform.md` is not planned work; do not build any of it unless asked, and only tick a stage's checkboxes for steps you were asked to do and finished.

`docs/spoilers/` holds what gives chambers away: each campaign chamber's notes (`chamber_<id>.md`: its idea, intended route, lure, restrictions and playtests; `docs/level_design.md`, guideline 52) and the idea pool (`ideas.md`), chamber ideas with no chamber yet. The author plays every draft cold before reading its notes, so read and write them when designing chambers, but never tell the author a chamber's key move, layout or route before they have played it: hand over only its address.

## Rules

- **After completing code changes**: Run `npm run lint:fix` and fix remaining errors, run `npm run build` (type-checks first) and fix any failures, then run `/delta-review` before responding. `npm run verify` runs the same lint (without fixing), the build, the bundle and asset checks and the engine checks, and changes no tracked file: `npm run bundle:check` (the files in `dist/assets`, totalled by kind: JS, CSS, images, audio and any other, each fails when it grows by more than both 10% and 10 KB over `scripts/bundle_baseline.json`; after a growth you accept, `npm run bundle:baseline` builds and records a new baseline), `npm run assets:check` (since the loading screen downloads every file under `src/assets/audio/` and `src/assets/images/`, each file under `src/assets/` must be imported, or named in a CSS `url()`, by a source the build ships (`src/` but `src/dev/`, and `index.html`), a mention in a comment not counting; the sprites' folder, read by name instead, holds exactly one `.webp` or `.png` per sprite, of a size its shape allows (read from the file's header), and no folder), `npm run smoke:engine` (every chamber file and every playground chamber loads with the rules under Node and settles its start, printing its state's size and hash), `npm run replay:check` (every chamber's recorded solution (the campaign's, since the playground chambers have none) completes with its expected moves, portals and final hash, and then no action changes the completed chamber or reports anything; every behaviour fixture in `scripts/fixtures/fixtures.ts` ends as pinned; both routes of every solver fixture in `scripts/solver_fixtures/solver_fixtures.ts`, on its chamber loaded with the layout checks, complete with their pinned counts and final hash), `npm run solver:check` (the solver's state key, its shortcuts against the rules' step and both searches against the solver fixtures' hand-counted pars, everything `docs/solver.md` lists under "How it's checked"), `npm run random:walk` (100,000 seeded random actions per chamber, per playground chamber and per fixture chamber, the fixture chambers read without the layout checks, each settling within the rules' pass cap, with the speed and the state's size; `--seed=` and `--steps=` change them) and `npm run chamber:check` (every chamber file and every playground chamber reads and validates without an error, every chamber in the play order has an id that is a whole number of 1 or more, used by no other chamber, whose file, `chamber_<id>.json`, holds exactly the layout the game loads for it, the playground list (`src/services/playground_catalogue.ts`) lists every playground chamber's file, the layout at place N being exactly the one in `playground_N.json`, the hint list (`src/services/hint_catalogue.ts`) names only chambers in the play order, each hint's id used once in its chamber, its lit tile holding its element (a box's start tile for a box), its trigger tile inside the chamber, and a timer hint waiting more than 0 seconds and naming a cancelling event, and each case in `scripts/fixtures/format_examples.ts` reports exactly the problems pinned for it, and the compiled format 2 example reaches exactly its pinned links (its group expanded) and refuses portals for good on exactly its pinned walls, every chamber file, every playground chamber, every fixture chamber and the example, compiled, answers wall, no portals and no element on the ring of tiles just outside its edge, then the element registry matches the format: the parser accepts every element's field, no two elements share a field, and every game event has exactly one owner, an element or the core step, and every element that blocks only while blocked has a blocked flag); it is the whole-project check that later stages extend (`npm run check` is the fix-then-build shortcut).
- **Testing in the browser**: After code changes that can be seen or played, also test them yourself with the Chrome tool when it is connected: run `npm run dev` in the background, open a new tab and exercise the change (keys, clicks, screenshots, console). Keep the tab silent, because the user may be listening to something in another tab. The Chrome tools cannot mute a tab, so after every page load, before pressing Start, run `const play = HTMLMediaElement.prototype.play; HTMLMediaElement.prototype.play = function () { this.muted = true; return play.call(this) }` in the page: every sound effect and the music play through audio elements, and nothing plays before Start. Close the tab and stop the dev server when done, and say in the report what was tested this way and what was not.
- **Game/Vue boundary**: `src/game/` is plain TypeScript and never imports Vue, vue-router, `src/components/`, `src/services/` or `src/chambers/`, nor uses `localStorage` or `sessionStorage` (both enforced in `eslint.config.js`). Screens drive it, not the other way around: `chamber_screen.vue` creates a `Level` on its canvas with the player's key bindings (a plain object, read once), sized in device pixels (refitted when the stage or the device pixel ratio changes; the drawing scales with the tile size alone; the tiles are sized as if the chamber were at least 16 tiles each way, so a smaller one is drawn no larger than that and sits centred in the stage, while the home menu's map always fills its box), calls `load` (also used for reset), `resize`, `dispose`, toggles `paused`, reads `started` and `elapsedHundredths` (the chamber clock) and `moves`, `portalsPlaced` and `framesPerSecond` (for analytics), reads `chamberWidth` and `chamberHeight` (to place a hint over its tile), gets `onCompleted` and `onStep` back (`onStep` after each step the rules take for a press, with the subject's tile, the step's events and whether it completed the chamber, never on a load; the screen sets hints off from it and from the clock), and in development calls `createReplay` for the completion dialog's Download solution and sets `frameStats` (`src/game/frame_stats.ts`), which the level tells of each frame, drawing and rules step, timing them only while it is set, and whose samples the screen hands to the performance view. `Input` queues presses in arrival order (a held key's repeat is dropped while its earlier press still waits). Each frame `Level` takes the oldest press as one action of the rules' step (`step` in `src/game/rules/step.ts`), which carries out every consequence of the action before it returns, so live play takes one action per frame, in the order pressed; while paused nothing is queued, and resuming forgets every press still waiting. Every move key press is a turn action: the subject faces that way without moving, unless it already faces that way, when it moves, as the rules say (there is no turn key; the rules' plain moves, which turn and step at once, are played only by the recorded solutions, the behaviour fixtures and the solver); it starts the clock and is logged like any press. `Level` draws only when the state changes or something on the canvas moves; idle frames draw nothing. A step that changes the state is drawn over time (the subject's glide, a slide along its path, the walk-out past the exit), and so are the other animations and effects, but none ever holds up a press: every press taken ends the running step drawing at once. When frames are drawn, how each animation and effect looks, its timings, the step events that start it, what it replaces or runs alongside, what a load clears, and what a slide holds back until the subject gets there (sounds, break-ups, the stop's settling, `onCompleted`) are in `docs/sprites.md` ("Steps" and each effect's section); their code is in `src/game/`. With `prefers-reduced-motion` (read by `Level` each time a step would start one) nothing is drawn over time. A load settles the chamber's start and plays the sounds of its events. `Level` reads the completion from the state after each step and then calls `onCompleted`; once the chamber is completed nothing runs, and every press, held repeats included, is dropped without cutting a walk-out or a slide onto the exit short. `moves` counts each step that puts the subject on another tile, a portal crossing included. `Level` logs every action it takes and the state's hash after it, and `createReplay` replays the log with the replay runner and refuses when any hash, the moves or the portals differ from the live run. The rules (`src/game/rules/`) play no sounds: they report what happens as `GameEvent`s, and after each step `Level` plays the matching `Sound` for each, in order, and counts the portals placed from them (which sound each event plays, and the exceptions: `docs/interface.md`, "Sounds"). They take actions (four moves, four turns, two shots, interact), which `Level` makes from the presses (`Input` maps the physical keys to `GameKey`s); a move key press is always a turn. A stricter lint block for `src/game/rules/` forbids importing `sound`, `music`, `audio_sources`, `renderer`, `input`, `level`, `tile_painter`, `element_drawings`, `step_animation`, `subject_pose`, `subject_turn`, `fizzle_particles`, `fizzler_field`, `fizzler_flashes`, `fizzler_splashes`, `light_barrier_band`, `light_barrier_reactions`, `box_fall`, `box_returns`, `destroyed_boxes`, `returned_boxes`, `mirror_bounces`, `element_transitions`, `exit_shadow`, `miss_ripple`, `portal_openings`, `portal_particles`, `ray_drawing`, `piece_number`, `sprite_set`, `sprite_sources`, `sprite_scaling`, `surface_noise`, `surface_tone`, `wear_marks`, `element_parts`, `element_detail`, `antline_drawing`, `chamber_preview` and `frame_stats`, and using `localStorage`, `sessionStorage`, `window`, `document`, `Audio`, `requestAnimationFrame` and `performance`; `tsconfig.scripts.json` type-checks the rules without the DOM. The solver (`src/solver/`) has a block of its own with the same bans, plus `@scripts/*`, Node's modules (`node:*`) and `process`, so it can also run in a Web Worker; it may import `src/game/`, never Vue, components, services or chambers. The chamber clock's rules are in `docs/interface.md` ("Chamber screen"). Services may import from `src/game/`: settings sets `Sound.masterVolume` and `Music.masterVolume` from the player's volumes and switches between the menu music and the chamber playlist (`docs/interface.md`, "Music"), and the asset preloader hands each audio player its downloaded file through `useAudioFile` in `audio_sources.ts`. `Sound.MENU_MOVE`, `Sound.MENU_ACCEPT` and `Sound.START` are interface sounds the game never plays: components play them, at the sound effects volume (when: `docs/interface.md`, "Sounds"). Game objects are never made reactive and per-frame data never passes through a `ref`: the screen writes the timer's text straight into its element each frame. The home menu's map (`chamber_preview.ts`) draws each chamber's settled start with the same renderer.
- **Rules are pinned, the look follows the sprite spec**: The rules are defined in `docs/elements.md` (each element, the step, and every change from the original game's rules) and pinned by the recorded solutions and the behaviour fixtures. Change a rule only when explicitly asked, and then in the same change re-record the solutions (and fixtures) it alters and update `docs/elements.md`. The chamber is drawn from the sprites `docs/sprites.md` describes, each drawn in code as an SVG in `art/sprites/` and exported to its file, but for the subject's painted sprites (`docs/sprites.md`): don't change how sprites are placed, their art or the palette unless asked, and change a sprite's art in its source, then export it again. There is no stand-in drawing: a sprite whose file is missing, refused or failed to download isn't drawn, so `npm run assets:check` requires every sprite's file, of a size its shape allows, and a new element's sprites need their files before they are added to the set. The palette (`src/game/palette.ts`) holds only the colours drawn by code, the background behind the floor, the shared shadow, a missed shot's ripple in each portal's colour, the particles rising from each open portal, in its own colours, the fizzlers' fields, from their blue sheet through their cyan light to the white of a shot's splash, the light barriers' bands, in the light barrier's teal (which has no CSS token) with their rim, light, edges and flare, the antlines' dots and their borders, unlit and lit, an emitter's ray, from its dark rim to its white-hot core, the strokes marking a carried mirror box's mirror, the surface detail's tints and marks, each drawn faint, the element detail's tints and a grate's marks, also faint, and the open exit's shadow at its darkest (the shared shadow and the last eight with no CSS token, as the menus don't use them); the background is mirrored by hand in `--color-chamber`, the ripple's colours in `--color-blue` and `--color-orange`, and the meaning colours (`docs/sprites.md`) by hand in the CSS tokens and the sprites, so change them together.
- **Keyboard ownership**: The game's `Input` owns the keys bound to its game keys (`src/game/key_bindings.ts`), read by physical position (`KeyboardEvent.code`) so they stay in place on every layout; while playing it calls `preventDefault` only for bound keys with a browser default and for bound keys with Ctrl held, never with Alt or Meta held. The mouse plays no part in the game but its left and right buttons, which only the two portals can be bound to (under Custom): a bound button's press anywhere in the window is that portal's press, and the pointer's movement is ignored. Screens own Escape, and the menus read `event.key`. While any dialog is open the game is paused and its input ignored, and a held (repeating) key acts in no dialog. A hint's card counts as a dialog: only Enter or a click on Continue closes it, after its first half second, and Escape does nothing while it shows. The layouts of controls (Default and Custom), which keys can be bound, how keys are labelled, Escape and browser Back in a chamber, the home menu's keys and pointer, and the dialogs' keys, the custom controls dialog's and the hint card's among them, are specified in `docs/interface.md` ("Keys", "Home menu", "Chamber screen" and "Dialogs"); keep it in step when changing any of them.
- **Desktop only**: Touch-first devices (`pointer: coarse`) get the desktop-only notice instead of the app. Do not add mobile layouts or touch controls.
- **Chambers**: A chamber of the campaign (the chambers under Play, in development and release alike: for now Chambers 1 to 30: the tutorial run, run 2's one chamber, run 3's two, run 4's three, run 5's two, run 6's two, run 7's two, run 8's one, run 9's four, run 10's three, run 11's two, run 12's two, then run 13's two) is a JSON file in `src/chambers/`, with a recorded solution next to it, and an entry in `src/services/chamber_catalogue.ts` (which the engine scripts read as their list of chambers, failing on a chamber file it doesn't list): a permanent `id` (1 or more, given in the order chambers were created: 1 is the tutorial run's first chamber, which took it from the old tutorial, now Playground 12, and each new chamber takes the id after the last chamber's, so no id is skipped (run 2's kept chamber, built as 8 beside drafts 5 to 7 that were cut before any was deployed, took 5, and run 5's combine, built as 13, took 12 when 5.2 was cut); giving a cut chamber's id to another, or renumbering ids, now and for every later chamber, needs no check of whether they were deployed and no question to the author: the analytics history or stored progress it mixes doesn't matter (the author's standing call, 2026-11-23); it names the chamber's files, keys its stored progress and its hints in the hint list and is sent as the analytics `chamber_id`, so changing one splits that chamber's analytics history), its layout and, optionally, a name the player sees instead of "Chamber N" in the home menu and the chamber-complete dialog (no chamber has one now). Its number is its position in the list, counted from 1, derived, never typed by hand; links (`/chamber/N`, where `/chamber/0` and a number with no chamber go home), the in-memory last chamber and the `chamber_number` analytics parameter follow it. `npm run chamber:check` fails on an id that is not a whole number of 1 or more, is used twice, or names a file that doesn't hold its chamber's layout. Chamber files are in format 2 (`"version": 2`, described in `docs/elements.md` under "Chamber format"): `ChamberData` (`src/game/chamber_data.ts`: a `version`, lists that may be left out, blocked walls (walls that refuse portals while blocked, a one-tile one linkable), link groups sharing the element ids, antlines (dotted lines on the floor from a button, switch or receiver to one element it links, by id, never a group, along corner tiles that share a row or a column; only drawn, lit while that button, switch or receiver is active, optional and meant mostly for the tutorial and the early chambers), an optional par block (the fewest moves and portals, each optional, filled by nothing yet); its element fields are typed from the element registry in `src/game/rules/element_registry.ts`, each by its definition's entry type) must accept the JSON import without a cast, so the type checker validates every chamber file, and `scripts/fixtures/format_examples.ts` types a format 2 example the same way. Type checking can't catch a misspelled or unknown field in an imported file, so the chamber loader (`src/game/rules/load_chamber.ts`) does: it reads a file as raw JSON, refuses any `version` but 2, and rejects what `docs/elements.md` lists under "What the validator rejects". The level and the home menu's map load every chamber through it and throw on a chamber it rejects, so `npm run chamber:check`, which runs it on every chamber file and every playground chamber, must pass. The playground chambers (`src/dev/playground/playground_N.json`, N from 1 to 12, format 2, edited by hand) are chambers outside the campaign for trying elements and ideas, which never need to be solvable; Playground 2 to 10 are the campaign's old chambers 1 to 9, which left it for good (Playground N was chamber N − 1), and Playground 12 is the old tutorial, which left it when the tutorial run's first chamber took its id. They have no permanent id: each is named "Playground N" after its place in `src/services/playground_catalogue.ts`, which lists them by hand, in order (plain TypeScript using nothing of Vite's, so the engine scripts read it too; `npm run chamber:check` fails on a playground file it doesn't list, or on a place whose layout isn't exactly its file's), and the game reaches them only through `src/services/playground.ts`, which numbers them, in development and production builds alike. Playground 1 is the one for trying every element: from the start, each direction tests one group, switched by the button one step that way (up the door and the exit, between blocked side walls; right two lasers crossing; down the fizzler, three light barriers side by side across the room (so its far row needs a box on the button) and a blocked wall in the bottom wall, taking portals while the button is held; left the ditches, and past them, down through a gap in the floor of the left arm, a slide room in the bottom left corner: slide floor throughout, with a fizzler field across it, held off by a button on the slide floor that the room's own box can hold down), and the middle room holds the four arrows, one of them, on the left, turned up by its own button below it while that is held, so stepping up off the button onto it turns it back under the subject, two boxes and a switch that sends them back and brings in a third, absent until then, beside the start; an antline leads to one element of each kind (up to the door, and to the exit, crossing a wall beside the door; right to a laser; down to the fizzler, to a light barrier, crossing a wall, and to the blocked wall, straight down under the fizzler and a light barrier; - **Persistence**: `localStorage` keys are prefixed `portal-2d.` and every access is wrapped in `try`/`catch` (storage can be blocked). Malformed values, unknown fields and a record of another version are ignored. Stored formats may change without a migration: a stored value that no longer reads is ignored and falls back to its default (friends' saves may be reset by updates). What is stored (the volumes, the legend, the controls, the playlist's place and the progress, the hints seen included), under which key, in which format, which values sync between tabs, and what is kept in memory only: `docs/interface.md`, "Saved data"; keep it in step.
- **Analytics**: `src/services/analytics.ts` sends Firebase Analytics events from production builds only (`npm run dev` sends nothing and logs each event to the console as `[analytics] <event>` with its parameters instead, so events can be checked there, but `npm run preview` serves a production build and sends real events), with no consent prompt. Its config holds only `apiKey`, `projectId` and `appId`; the SDK fetches the measurement ID itself. Any failure (unsupported browser, ad blocker) silently drops events and never affects the game. Every event and its parameters are listed in `docs/interface.md` ("Analytics"); keep that list in step. Event and parameter names are permanent: renaming one splits its history.
- **Assets**: Import assets from `src/assets/` so Vite fingerprints them; nothing new goes in `public/`. Run `npm run audio:normalize` after adding or replacing an MP3, so it plays as loud as the other effects, or the other music. Fonts come from Google Fonts via `<link>` in `index.html`.
- **Loading screen**: Every visit (desktop only) opens on `loading_screen.vue`, which downloads every file under `src/assets/audio/` and `src/assets/images/` (`asset_preloader.ts` finds them at build time), but the chamber playlist's streamed tracks (`src/assets/audio/music/streamed/`), then waits for Start; how it hands each file to the game, its timings and how a failed or stalled file is handled: `docs/interface.md`, "Loading screen". Delete asset files that are no longer used, since they are downloaded too, or for a streamed track, deployed (`npm run assets:check` fails on one). The preloader's font list must match the faces requested in `index.html`. Audio is handed to the game's players as an in-memory copy, because Firebase varies responses by encoding and a media request would miss the cache and download the file again; the players (created through `createAudioPlayer`) download nothing on their own until they first play.
- **Recorded solutions**: `src/chambers/chamber_N.solution.json` is a run of the chamber whose permanent id is N (only the campaign's chambers have one; the playground chambers never need to be solvable), recorded press by press (`ReplayData` in `src/game/replay_data.ts`; each press is an action, such as `"up"`, `"turnLeft"` or `"blue"`), with what replaying it must give and the hash of the chamber it was recorded on (taken from the chamber as read, leaving out its antlines, which are only drawn, so a chamber with none keeps the hash it had). Record one by completing the chamber in `npm run dev` and pressing Download solution in the completion dialog (development builds only; it refuses when the run doesn't replay the same way), which names the file by the chamber's permanent id (it matches the file's number), then move it next to the chamber. Record it again whenever its chamber file changes (the replay check reports a changed chamber; a change to its antlines alone needs none) or a rule change alters its route. Behaviour fixtures live in `scripts/fixtures/`, outside the catalogue: `fixtures.ts` pins, on tiny chambers of its own, how the rules play each change from the original rules and each element the original game didn't have (the light barrier, the blocked wall a link switches, the slide floor, the arrow a link turns, the emitter, its ray, the receiver, the mirror box and the box that starts absent until a link brings it in, and the destroyed box a link reaches, absent until that link brings it in again), and each rule of the interaction table in `docs/elements.md` that no other fixture plays, so every rule there names its fixtures. Solver fixtures live in `scripts/solver_fixtures/`: tiny chambers that pass the layout checks, each with a fewest-moves and a fewest-portals route counted by hand (never by a search, since they are the reference the solver is checked against) and a short argument for why each count is optimal.
- **No test suite**: This project has no tests by design. TypeScript, the type-aware lint rules and the engine checks (the recorded solutions, behaviour fixtures and solver fixtures replayed by `npm run replay:check`, the solver check, and the random walk) are the safety net — do not weaken `strict` or `noUncheckedIndexedAccess`, and do not add `any` to silence an error.
- **TypeScript projects**: `tsconfig.json` only references `tsconfig.app.json` (browser, `src/`, extends `@vue/tsconfig/tsconfig.dom.json`), `tsconfig.node.json` (`vite.config.ts`, extends `@tsconfig/node24`) and `tsconfig.scripts.json` (Node without the DOM, extends `@tsconfig/node24`: `scripts/`, the rules in `src/game/rules/`, the solver in `src/solver/`, the shared files they import (the chamber catalogue, the playground list and the hint list among them), the chamber JSON, the playground chambers' and the fixture and solver fixture chambers; a file the scripts reach must be in its `include`, or the build fails; scripts import each other through its own `@scripts/` alias). An option the bases don't already cover must be set in all three.
- **Deploy**: `npm run deploy` runs `npm run verify` (which builds into `dist/`, git-ignored), stopping if any check fails, then `firebase deploy --only hosting` (project `portal-2d`); `npm run deploy -- -f` skips the checks and runs only `npm run build` before deploying. `firebase.json` rewrites every path to `/index.html` for history-mode routing.

## TypeScript

- No semicolons. Single quotes. One class per file. Named exports (but the router's default export in `src/router.ts`).
- Files `snake_case`; classes, interfaces and type aliases `PascalCase`; functions and variables `camelCase`.
- Full descriptive names — no `el`, `p`, `btn`. Allowed short names: `i`, `j` (loop counters), `x`, `y` (coordinates), `dx`, `dy` (deltas), `ctx` (canvas context).
- Always import with the `@` alias (mapped to `src/`; scripts reach other scripts with `@scripts/`). No relative paths, no file extensions but a `.vue` component's, a JSON file's or an asset's. `import type` for type-only imports.
- No object shorthand: write `level: level`, not `level` (enforced). An object literal, destructuring or export with any property breaks across lines, one property per line, while an import stays on one line; arrays with two or more items go one item per line (enforced).
- No TypeScript `enum`: use string-literal unions, with a const object when named values help.
- Indexing a `Record` or array yields `T | undefined`: handle the miss rather than asserting it away with `!`.
- Prefer getters over methods for parameterless functions that only read state.
- Unused parameters: `_`, `__`, `___`.
- Comments: a JSDoc block on every class and function (no types — TypeScript declares them), an end-of-line comment on each field's first declaration, plain comments above non-obvious logic.

## UI

- Always use the `frontend-design` skill when changing the UI.
- Direction: test-facility signage: cool light panels on a seamed wall, thin rules, chamber numbers as large sign numerals, and the game's own colours as the only accents: blue marks interaction and success, orange is the second portal, the floor button's red marks caution (actions that discard progress), and the test subject's green marks a completed chamber on its row. Keep these meanings consistent. How each screen looks (the loading screen's wall, the home screen's room photo and menu, the chamber screen's stage, rail, sign, legend and performance view, the dialogs) is specified in `docs/interface.md` ("Look"); keep it in step. The chamber sign has a pictogram for each kind of element, so a new element needs one.
- Tokens live on `:root` in `src/assets/styles.css` (`--color-wall`, `--color-panel`, `--color-rule`, `--color-white`, `--color-ink`, `--color-ink-muted`, `--color-blue`, `--color-blue-deep`, `--color-orange`, `--color-red`, `--color-red-deep`, `--color-subject`, `--color-chamber`, `--color-stage-edge`, plus `-rgb` triplets of panel, white, ink, blue and subject for alpha, and `--font-display`, `--font-body`, `--ease-out` and `--menu-row-height`). Use tokens, not new colours.
- Type: `Oxanium` (`--font-display`) for sign lettering (sign numerals, the chamber sign's number in its light weight, its only use, titles, the menu's rows, `.button-sign`, a volume's number and Off) and for every time readout (the chamber clock and the menu's best times, since `Chakra Petch`'s digits vary in width and have no tabular form), `Chakra Petch` (`--font-body`) for everything else, ruled labels and keycaps included. Oxanium is not condensed: the home menu's first column is wide enough for the development-only Playground row, and dialog titles are sized so "Chamber 10 complete" fits on one line.
- CSS colours, and the game's canvas colours in its palette, are always `rgba()`, never hex. `border-radius` in `rem` (exception: `50%` for circles).
- Repeated CSS goes to `src/assets/styles.css`; component-specific styles stay in scoped `<style>` blocks.
- Accessibility floor: visible keyboard focus, keyboard-operable dialogs, volume sliders and the legend's fold toggle, and `prefers-reduced-motion` respected (the global rule in `styles.css` cuts CSS animations and transitions; smooth scrolling and the canvas check the query themselves).
- Copy is sentence case, plain verbs; a button says what it does ("Restart chamber", not "OK"). Signage labels may be shown in capitals with `text-transform`; the text itself stays sentence case.
- CSS comments: `/* ==== */` block dividers for major sections, a short phrase above a rule for its purpose.

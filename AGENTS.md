## Project

Portal 2D — a desktop-only, keyboard-driven puzzle game: the player crosses grid-based test chambers using a pair of portals (Vite + Vue 3, TypeScript, Composition API with `<script setup>`, vue-router, ESLint + @stylistic + type-aware typescript-eslint via @vue/eslint-config-typescript). It is a static site on Firebase Hosting; there is no backend.

`todo/` holds the author's roadmap: an overview (`README.md`) and one file per stage (`04b_campaign.md` and `05_creator_platform.md`; stages 00, 01, 03 and 04a are done, stage 02 stopped after its prototype, and their files are removed; what stage 02 learned is in `docs/solver.md`; the 04a decisions 04b cites are copied into it), and `future.md`, ideas for mechanics beyond the plan and how a mechanic was built. They are not planned work; do not build any of it unless asked, and only tick a stage's checkboxes for steps you were asked to do and finished.

`level_design_research.md` (in the root) is outside research on puzzle level design: tips by topic for designing this game's chambers, drawn from the makers of similar games and generic writing, those `docs/level_design.md` lacks listed as candidate guidelines, a pattern catalog mapped to this game's elements, and chamber ideas. Read it when designing chambers; it is reference, not rules or planned work.

- **Game/Vue boundary**: `src/game/` is plain TypeScript and never imports Vue, vue-router, `src/components/`, `src/services/` or `src/chambers/`, nor uses `localStorage` or `sessionStorage` (both enforced in `eslint.config.js`). Each frame `Level` takes the oldest press as one action of the rules' step (`step` in `src/game/rules/step.ts`), which carries out every consequence of the action before it returns, so live play takes one action per frame, in the order pressed; while paused nothing is queued, and resuming forgets every press still waiting and every key held; the window losing focus forgets every key held, since their keyup goes elsewhere. A move key pressed while the turn key is held (Shift by default) is a turn action: the subject faces that way without moving, unless it already faces that way, when it moves, as the rules say; it starts the clock and is logged like any press. `Level` redraws when the state changes, and while a step is being drawn (`StepAnimation`, `src/game/step_animation.ts`: about 120 ms from the state before it to the state after it, eased out and started one frame back, so the press's own frame already shows part of it; a slide along its path at one tile every 60 ms, a portal crossing counting as two, its last tile eased out, so a six-tile slide takes about 0.42 s; a step that completes the chamber with the subject arriving on the exit the way out of its outer wall walks it out: no easing, a move at 180 ms a tile, a slide at its own pace, across the exit and on until it is a whole tile past the chamber's edge, then held there) every frame, paused or not, until a frame draws its end, which the renderer then draws exactly as the plain state; it also draws every frame, paused or not, while a fizzler's field or a light barrier is on, anything glows (a laser that is on or an open portal whose glow has a file), a portal gives off particles (while one is open, and for 0.2 s after one closes or moves), pieces break up, a box falls or flies home, a missed shot ripples, a fizzler's field splashes, a light barrier's band reacts, a portal opens, the subject turns, or an arrow, a blocked wall, a ditch, a door, the exit, a fizzler, a laser, a light barrier or a receiver's eye changes, and once more when that stops (a ray's glow, held steady, isn't among them); otherwise idle frames draw nothing. A step that reports `fizzled`, or `portalFizzled` (a fizzler switching on closed a portal facing it), breaks up the portals it took (`FizzleParticles`, `src/game/fizzle_particles.ts`: each portal open before it and closed after it; with `portalFizzled` alone, only a portal whose wall side faced a fizzler that is on after it, so one a blocked wall closed in the same step still just vanishes), replacing pieces still drifting unless it took nothing, or it is a later part of the same slide, whose pieces join them. A step that reports `boxDestroyed` drops each box a ditch destroyed into the pit (`BoxFall`, `src/game/box_fall.ts`), replacing a fall still running unless it dropped nothing, found with `findDestroyedBoxes` (`src/game/destroyed_boxes.ts`). A step that reports `boxDestroyed`, `carriedBoxDestroyed` (a box carried into an active fizzler) or `boxSentBack` (a link sent a box home) sends each box that went back to its start home (`BoxReturns`, `src/game/box_returns.ts`, finding them with `findReturnedBoxes` in `src/game/returned_boxes.ts`: every box destroyed where it lay, the one carried, and every other box that went from elsewhere to its start): its pieces fly home from where it was, or, for one that fell, it gathers at its start, alongside the boxes still on their way, a box sent home again starting over. A portal shot the rules refuse ripples where `shotStop` says it stopped (`MissRipple`, `src/game/miss_ripple.ts`), replacing a ripple still spreading; a refused crossing or interact shows none, a shot tried while carrying a box never leaves, so it shows none and no field splashes or band reacts for it, and a shot from inside a fizzler that is on reports nothing and shows none. Where a fizzler that is on stopped the shot, its field splashes from the point the shot met on its face (`FizzlerSplashes`, `src/game/fizzler_splashes.ts`), alongside any splash still running, which a load clears. Where a light barrier that is on stopped the shot, its band reacts too, and so does one the subject walked into: a move, or a turn the way it already faced, its own tile letting it go that way, that left it on its tile, a slide stopping in front of one not counting (`LightBarrierReactions`, `src/game/light_barrier_reactions.ts`), alongside the reactions still running; a band still reacting takes no new one, and a load clears them. Any step that opens, moves or closes a portal, a slide's legs included, starts the new portal's particles rising and the old one's fading (`PortalParticles`, `src/game/portal_particles.ts`), which a load clears. A step that reports `fizzled`, a slide's leg as the subject reaches the field's tile, flashes the field the subject is caught in from its tile (`FizzlerFlashes`, `src/game/fizzler_flashes.ts`), alongside any flash still running, which a load clears. Any step that turns an arrow rotates its chevron, any step that switches a blocked wall slides its steel apart or shut, any step that switches a ditch slides its grate in or out, any step that opens or closes a door or the exit slides it, any step that switches a fizzler off or on fades its field out or in, its connectors' lit slot fading with it, any step that switches a laser fades it, any step that switches a light barrier unfolds its band or folds it away, its end plates' lit slots with it, and any step that lights or darkens a receiver fades its eye (`ElementTransitions`, `src/game/element_transitions.ts`, comparing each receiver's lit flag as it compares blocked flags), from where it is drawn if it was still changing; a ray and an emitter's lens change at once with the step. With `prefers-reduced-motion` the glows hold steady, the fizzlers' fields hold still, the light barriers' edges hold steady, no particles rise, nothing breaks up, flashes, splashes, reacts, falls, flies home, opens, slides, turns, fades, unfolds or ripples and only changes are drawn. Part way through a step, the subject and a box it carries through it are drawn at the subject's pose (`src/game/subject_pose.ts`): a move glides one tile, a portal crossing slides into the entry portal, facing it, then out of the exit one, each half clipped to its tile, and a slide goes the same ways leg by leg along its path, a walk-out carries it on past the exit, unclipped, until the chamber's edge cuts it off, the distance still to go rounded to whole canvas pixels, the subject drawn as one of its two sprites (on a layer of its own while the chamber is completed, the exit's shadow laid over its pixels only, so it darkens on the exit, or, on the chamber screen, where the exit is see-through, fades out there) (`subject_holding_box` while it carries a box, a mirror box's mirror marked over it, else `subject_holding_gun`); everything else shows the state after the step at once, but the subject turns (`SubjectTurn`, `src/game/subject_turn.ts`) whenever the way it is drawn facing changes: a turn in place, a move another way, a walk into a wall, into a portal and along a slide, from the angle drawn, the shorter way round (a half turn clockwise), over about 0.1 s a quarter turn and 0.15 s a half, eased out and started one frame back; a press never cuts a turn short (the next turn carries on from the angle drawn), and coming out of a portal, or a press ending a crossing before it came out, it faces its new way at once; a load clears it. A load or a resize redraws at the latest frame's time, so a step being drawn never goes back. Only a rules step that changes the state starts one; every press taken ends the running one at once (a new key never waits), even a press that changes nothing; a load and a reset show their state at once; with `prefers-reduced-motion` (read by `Level` each time a step would start one) nothing is drawn over time. Sounds, the counters, the log and `onCompleted` stay in the frame that takes the press, and the clock is unaffected, but for a step that slid, drawn over time: the counters and the log stay at the press, while what happened on each tile it entered (its sounds, a fizzle's break-up) waits until the subject is half way into that tile, or through the portal onto it, and its stop and settling (buttons, doors, the element transitions, `onCompleted`) until the slide ends, but for reaching the exit, heard with the last tile; until then everything but the subject is drawn as the state on the last tile it has reached. - **Chambers**: A chamber of the campaign (the chambers under Play, in development and release alike: for now only Chamber 1, the tutorial) is a JSON file in `src/chambers/`, with a recorded solution next to it, and an entry in `src/services/chamber_catalogue.ts` (which the engine scripts read as their list of chambers, failing on a chamber file it doesn't list): a permanent `id` (1 or more, given in the order chambers were created: 1 is the tutorial's, and new chambers take 2, 3 and so on; it names the chamber's files, keys its stored progress and is sent as the analytics `chamber_id`, so changing one splits that chamber's analytics history), its layout and, optionally, a name the player sees instead of "Chamber N" in the home menu and the chamber-complete dialog (no chamber has one now). Its number is its position in the list, counted from 1, derived, never typed by hand; links (`/chamber/N`, where `/chamber/0` and a number with no chamber go home), the in-memory last chamber and the `chamber_number` analytics parameter follow it. `npm run chamber:check` fails on an id that is not a whole number of 1 or more, is used twice, or names a file that doesn't hold its chamber's layout. Chamber files are in format 2 (`"version": 2`, described in `docs/elements.md` under "Chamber format"): `ChamberData` (`src/game/chamber_data.ts`: a `version`, lists that may be left out, blocked walls (walls that refuse portals while blocked, a one-tile one linkable), link groups sharing the element ids, antlines (dotted lines on the floor from a button, switch or receiver to one element it links, by id, never a group, along corner tiles that share a row or a column; only drawn, lit while that element is unblocked, optional and meant mostly for the tutorial and the early chambers), an optional par block (the fewest moves and portals, each optional, filled by nothing yet); its element fields are typed from the element registry in `src/game/rules/element_registry.ts`, each by its definition's entry type) must accept the JSON import without a cast, so the type checker validates every chamber file, and `scripts/fixtures/format_examples.ts` types a format 2 example the same way. Type checking can't catch a misspelled or unknown field in an imported file, so the chamber loader (`src/game/rules/load_chamber.ts`) does: it reads a file as raw JSON, refuses any `version` but 2, and rejects what `docs/elements.md` lists under "What the validator rejects". The level and the home menu's map load every chamber through it and throw on a chamber it rejects, so `npm run chamber:check`, which runs it on every chamber file and every playground chamber, must pass. - **Persistence**: `localStorage` keys are prefixed `portal-2d.` and every access is wrapped in `try`/`catch` (storage can be blocked). Stored: the sound effects and music volumes (`portal-2d.sound-volume` and `portal-2d.music-volume`, 0 (Off) to 100 in steps of 10, 100 playing as loud as the game did before it had volumes, so the default; read once per visit, so not synced between tabs), whether the chamber screen's controls legend is open (`portal-2d.legend-open`, kept the same way), the controls under `portal-2d.key-bindings` (`{layout, custom}`: the layout in use, `arrow-keys` (shown as Default) or `custom`, and the Custom keys, a plain object, game key → key (its `KeyboardEvent.code`, `Control` or `Shift` for either side), or null until Custom is first picked; Default's keys are never stored, so a change to them always takes effect; Custom keys are read game key by game key, a stored key that can't be bound (the mouse buttons once bound, `MouseLeft` and `MouseRight`, included) or is already taken falls back to that game key's Default key, and if that is then taken every game key goes back to Default; a layout that isn't one (the retired `wasd-mouse` included), or Custom with no keys, falls back to Default; renaming a game key or a key name sends a stored binding of it back to Default; unlike the progress, it is not synced between tabs, so a tab keeps the controls it loaded until it reloads), the chamber playlist's place (`portal-2d.music-track`: the position in its list, from 0, of the last track it moved to, so the next visit's list carries on after it once the opener has played; missing, malformed or past the end of the list, the list starts from its top; written by every tab, read once per visit), and the progress under one versioned key, `portal-2d.progress` (`{version: 3, chambers: {<id>: {completed, bestTime, attempts}}}`, by permanent chamber id; best times in hundredths of a second, attempts counted on each opening, Restart chamber and Play again; version 3 since the tutorial took id 1 from the chamber that had it, so every save from before is ignored). Reset progress under Settings stores an empty record. Malformed values, unknown fields and a record of another version are ignored. Stored formats may change without a migration: a stored value that no longer reads is ignored and falls back to its default (decision 13 in `todo/README.md`: friends' saves may be reset by updates). Every save writes the whole record, so each tab takes over the record whenever another tab saves it (the `storage` event). The last chamber opened (its list, the campaign or in development the playground chambers, and its number, which the home menu highlights on the way back) is kept in memory only.
- **Analytics**: `src/services/analytics.ts` sends Firebase Analytics events from production builds only (`npm run dev` sends nothing and logs each event to the console as `[analytics] <event>` with its parameters instead, so events can be checked there, but `npm run preview` serves a production build and sends real events), with no consent prompt. Its config holds only `apiKey`, `projectId` and `appId`; the SDK fetches the measurement ID itself. Any failure (unsupported browser, ad blocker) silently drops events and never affects the game. Events: `chamber_start` (opened, or Play again), `chamber_restart` (Restart chamber confirmed), `chamber_quit` (Exit chamber or browser Back confirmed; not Back to menu or Next chamber after finishing, nor closing the tab), `chamber_abandon` (the page closed, reloaded or left for another site before finishing; at most once per attempt, and a lower bound, since events sent as a page goes away can be lost; a page restored from the back/forward cache carries on, so an attempt can be abandoned and later still end another way) and `chamber_complete`, each with `chamber_id`, `chamber_number` (its position in the play order, counted from 1, so Chamber 1 sends 1 for both) and `attempt` (the chamber's attempt count on this device, cleared by Reset progress; a restart ends attempt N and the next run is N + 1), all but `chamber_start` also with `time_ms` (the time shown), `moves` (steps that put the subject on another tile), `portals` (portals placed, misses not counted), `pauses` (times the pause menu was opened during the attempt, the one that led to a restart or an exit included) and, once it can tell, `fps` (how often the level's frame loop ran since the chamber was loaded, paused or not, gaps of over a second between frames left out, rounded; it follows the monitor's refresh rate, so it shows a slowdown on one machine rather than comparing machines), and `chamber_complete` also with `first_completion` and `new_best` (1 or 0; after Reset progress the next completion counts as first again). Restart chamber sends no `chamber_start` of its own, so runs = `chamber_start` + `chamber_restart`; `setting_change` (a volume changed, sent once it has stayed put for a second, unless it is back where it was last sent: `setting`: sound or music, `volume`: 0 to 100, and `enabled`: on, or off at 0, kept from the on/off switches the volumes replaced), `controls_change` (another layout of controls put in use under Settings, not the one already in use: `layout`: default or custom; binding a key sends nothing), `progress_reset`, `changelog_open` (stepping into the changelog, not just highlighting its row), `feedback_open` and `link_open` (`link`: the page's name on its row, `url`); `loading_complete` (the loading screen's bar is full and Start appears: `duration_ms`, the time since the page started loading, and `failed_files`, the files that didn't download or were refused as sprites; a visit left before then sends none, and pressing Start sends nothing), `asset_failed` (a file the loading screen downloads didn't download or was refused as a sprite, once per file: `file`, where it sits in `src/assets`, such as `images/chamber/box.webp` (a build turns a small file into a data URL, so its address names nothing), `kind`: audio or image, and `reason`: download or refused; at most 10 per visit), `desktop_only_shown` (a touch-first device got the desktop-only notice) and `exception` (Google Analytics' standard event for an error: one thrown and not caught, a promise rejected and not handled, or, in production builds, an error in a screen, which Vue would log to the console and which is still logged there; `description`: the error's name and message, or its text, cut to 100 characters, and `source`: page, promise or screen; an error event carrying no error, from a script on another site or the browser's ResizeObserver notice, is left out; each description once per visit, at most 10 per visit). Event and parameter names are permanent: renaming one splits its history.

## TypeScript

- No semicolons. Single quotes. One class per file. Named exports (but the router's default export in `src/router.ts`).
- Files `snake_case`; classes, interfaces and type aliases `PascalCase`; functions and variables `camelCase`.
- Full descriptive names — no `el`, `p`, `btn`. Allowed short names: `i`, `j` (loop counters), `x`, `y` (coordinates), `dx`, `dy` (deltas), `ctx` (canvas context).
- Always import with the `@` alias (mapped to `src/`; scripts reach other scripts with `@scripts/`). No relative paths, no file extensions but a `.vue` component's, a JSON file's or an asset's. `import type` for type-only imports.
- No object shorthand: write `level: level`, not `level` (enforced). An object literal, destructuring or export with any property breaks across lines, one property per line, while an import stays on one line; arrays with two or more items go one item per line (enforced).
- No TypeScript `enum`: use string-literal unions, with a const object when named values help.
- Indexing a `Record` or array yields `T | undefined`: handle the miss rather than asserting it away with `!`.
- Prefer getters over methods for parameterless functions that only read state.
- Unused parameters: `_`, `__`, `___`.
- Comments: a JSDoc block on every class and function (no types — TypeScript declares them), an end-of-line comment on each field's first declaration, plain comments above non-obvious logic.

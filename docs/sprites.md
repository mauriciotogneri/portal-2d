# Chamber Sprites and Effects

How the chamber is drawn. Its art is one image file per sprite, which the game composes tile by tile, choosing each by its element's state and its neighbours; the first part of this file is the spec to draw them to. Over and between the sprites the game draws effects in code, from no sprite: the glows' pulse, the portals' opening and particles, the fizzlers' fields, the light barriers' bands, the rays, the antlines, the surface and element detail and the exit's shadow, and every animation, from a step's glide and the subject's turn to the elements switching, the break-ups, the boxes' fall and flight home and a missed shot's ripple. The rest of this file says how each looks, what starts it, what it runs alongside and what a load clears.

The game draws the chamber and the home menu's map from these files. A sprite whose file is missing, can't be decoded or has the wrong size isn't drawn at all, so `npm run assets:check` (part of `npm run verify`, which every deploy runs unless forced with `-f`) fails when a sprite has no file, more than one, or one of a size its shape doesn't allow, and when the folder holds a file that isn't a sprite's, or any folder. In `npm run dev`, a file in the folder that isn't a sprite's, or of the wrong size, is logged as an error in the browser's console.

## Files

- **Folder:** `src/assets/images/chamber/`. The loading screen downloads every file in it, so keep nothing else there.
- **Name:** exactly as listed under [the set](#the-set), with `.webp` (smaller, preferred) or `.png`. One file per name.
- **Transparency:** everything around the drawn object is fully transparent. The floor, `slide_floor`, the three strips, `ditch_bridged`, `door_closed` and `exit_closed` fill their tiles; the rest don't, the emitters' and receivers' housings included, which leave the wall they sit on showing round them.
- **Weight:** WebP at high quality; the whole set is about 220 KB.

## Sources

Every sprite but the subject's two is drawn in code as an SVG in `art/sprites/`, named like its file and sized like it, never built or downloaded. Change a sprite's art there, then export it again, from the project's root: with Inkscape to a PNG, then to WebP in the folder:

```sh
inkscape art/sprites/box.svg --export-type=png --export-filename=box.png
convert box.png -quality 90 -define webp:alpha-quality=100 src/assets/images/chamber/box.webp
```

Add `-alpha off` to the second command for the sprites that fill their tiles: the floor, `slide_floor`, the three strips, `ditch_bridged`, `door_closed` and `exit_closed`. The subject's two sprites are painted, with no SVG, and exported with commands of their own (see [the subject](#the-subject)).

The element detail (see [element detail](#element-detail)) is laid over parts of some sprites, whose shapes are copied by hand from their sources into `src/game/element_parts.ts`: the box's plates, the mirror box's plates and mirror, the button's and the switch's plate, clamps and dome, the turntable's face, the grate's plate, bars and frame (`ditch_bridged`), and the pit's 82 px side (`ditch`). Changing one of those shapes in its source means changing it there too.

## Size

- **Tile:** 256 × 256 px. The game shrinks each sprite once to the tile size on screen. In a 1920 × 1080 window, whose chamber screen leaves a stage of 1488 × 1016 page pixels, Playground 2 (20 × 20) gets 50 px tiles, and Playground 12, the old tutorial (12 × 10), 63 px, since a chamber under 16 tiles either way gets the tiles a 16 × 16 one would; at pixel ratio 2, 101 and 127 px. The home menu's map draws them smaller still.
- **Overhang:** a sprite that spills past its tile (a glow, a portal reaching into the room) is 384 × 384 px: its tile is the centred 256 px square, with 64 px of margin on every side. Any sprite but a strip may overhang; the game tells by the file's size.
- **Strips:** `wall`, `blocked_wall` and `ditch` are 1280 × 256 px, five tiles side by side (see [joins](#joins)).
- **Any other size** is refused, and the sprite isn't drawn.

## Look

- **View:** straight down, no perspective. A wall shows its top, never a front face.
- **Light:** from directly overhead, so every side of an object is shaded the same: no highlight on one side, no shadow on the other.
- **Shadows:** don't draw a shadow falling outside the object. The game adds one shared drop shadow, made from each sprite's shape, under what stands raised (walls, blocked walls, closed doors, the closed exit, switches, boxes, the subject): a soft dark rim all round, with no offset, since the light is overhead. Walls cast theirs as one mass, so a run of walls has one shadow along its open sides.
- **Readable small:** every sprite must still read at 40 px. On and off must differ at a glance, and the subject's facing must show from its shape alone.
- **Colours:** the ones that carry a meaning are listed here and copied by hand into the CSS tokens (`src/assets/styles.css`), since the menus use the same colours (crimson, teal, cyan, amber and pale gold, which they don't use, have no token). Keep blue and orange off every other sprite, so nothing is mistaken for a portal; the exceptions are the fizzler's field, drawn in code (see [fizzler field](#fizzler-field)): its see-through blue (22, 85, 211 at 50 %), deeper than the blue portal and with no edge lines, and its cyan light (126, 218, 255, at its palest 191, 237, 255), lighter and bluer than the antlines' muted cyan; the dark cobalt (36, 48, 96) of its connectors' unlit slots; and the subject's orange jumpsuit and blue-lit portal gun (see [the subject](#the-subject)). The surface detail, drawn in code, is grey and faint throughout, so it carries no meaning (see [surface detail](#surface-detail)), and the element detail, drawn in code over the elements' sprites, is faint and keeps off every part that carries one (see [element detail](#element-detail)). The antlines, drawn in code, keep off them too: their cyan is clear of the blue portal and of the light barrier's teal, and their amber yellower than the orange portal. Changing one of these means redrawing the sprites that use it, along with its CSS token.

## Joins

Walls and open ditches join their neighbours: a run of walls reads as one raised mass, bevelled only where it meets something else, and a run of open ditches as one pit. Each comes as a strip of five tiles, which the game cuts into 128 px quarters. Each quarter of each tile is taken from the strip tile that matches three neighbours: the two tiles beside its corner and the one diagonal between them.

| # | Strip tile | Shows | Gives the quarters where |
|---|------------|-------|--------------------------|
| 1 | Lone | One wall tile with floor all round | Both tiles beside the corner are open |
| 2 | Horizontal run | Walls left and right, floor above and below | The tile above or below is open, the one left or right is wall |
| 3 | Vertical run | Walls above and below, floor left and right | The tile left or right is open, the one above or below is wall |
| 4 | Inner corners | Walls on all four sides, floor on all four diagonals | Both tiles beside the corner are wall, the diagonal open |
| 5 | Solid | Wall all round | Both tiles beside the corner and the diagonal are wall |

For example, a wall tile's top-left quarter comes from strip tile 2 when the tile above it is floor and the tile to its left is wall.

Quarters from different strip tiles end up side by side, so:

- every open side gets the same bevel, 48 px wide all along, so a portal fits on it;
- the top surface's texture tiles seamlessly, any edge meeting any other;
- details (rivets, seams, lights) stay off the 128 px midlines and the tile edges, where they would be cut.

Outside the chamber counts as open, so walls along the chamber's edge are bevelled on their outer side too, and the chamber reads as a raised block with a finished border.

A blocked wall, which refuses portals, is drawn from its own strip, `blocked_wall`, while blocked, but joins every wall alike, so both kinds make one mass with one shadow, each tile cut from its own kind's strip. Its strip keeps the wall strip's shape exactly, bevels and seams in the same places, so where the two kinds meet their edges line up and only the surface changes. A blocked wall a link reaches is drawn with the walls as a wall, and while it is blocked its `blocked_wall` tile is painted over it among the blockers, so only its surface changes, with no mark of its own, the steel sliding apart into the walls beside it or shut when it is switched (see [sliding](#sliding)); one no link reaches never changes, so it is drawn with the walls in its own strip, or as a wall when it starts unblocked.

In the ditch strip, read "wall" as "open ditch" and "floor" as anything else. It shows the pit's inner sides, the same depth everywhere: 82 px wide, fading from the lit rim to near black, lined with seams that crowd closer together as they go down, so the pit reads as a deep shaft. A bridged ditch is drawn on its own (`ditch_bridged`) and ends the pit. While a ditch is switched it is drawn as part of the pit, its grate sliding in or out over it (see [sliding](#sliding)).

## Glow

The three glow sprites are drawn over everything but the portals' particles, a fizzle's pieces, a box's pieces flying home and a missed shot's ripple, and added to the colours beneath, so they brighten and never darken. Their strength pulses slowly, all together, between 60 % and full. Draw only the light, at full strength: colour fading to transparent, with no beam or portal in it. A missing glow file just means no glow, and no frames drawn for it. With reduced motion, and in the home menu's map and the gallery, the glow holds steady at 80 %.

The rays' glow, drawn in code from no sprite (see [rays](#rays)), is added with the glow sprites, after the lasers' and before the portals', but always held steady at 80 %, so a lit ray never needs a frame of its own. It is painted on a layer of its own, where each spot keeps its brightest, so a ray's corners and two rays crossing aren't lit twice, and kept until the rays run elsewhere or the tile size changes.

## Opening

When a shot opens a portal, the game grows it open on its wall from its own sprite, so there is nothing extra to draw: it grows from the middle of its oval, past its size to about 110 %, and settles back, in about 0.2 s, fading in over the first 40 ms, while its glow rises with it. The game takes the oval's middle as 23.5 px of the 256 px tile in from the tile's top edge, as drawn (`src/game/portal_openings.ts`), and the particles take the oval as 97.25 by 19.75 px about it (`src/game/portal_particles.ts`), so change them there too if the oval moves or changes size. A step that reports `bluePortalOpened` or `orangePortalOpened` starts it, replacing an opening of that portal still running. The portal it replaces, if any, still vanishes at once; one that moves or closes while it opens is drawn as it is, and one that breaks up while it opens breaks up whole (see [fizzle](#fizzle)). Loading or restarting the chamber clears every opening. With reduced motion, and in the home menu's map and the gallery, a portal appears at once.

## Particles

Each open portal gives off particles, drawn by the game in code from no sprite (`src/game/portal_particles.ts`), in its own colours from the palette: soft shafts of light standing on the oval and rising into the room, and small sparks climbing them. They are painted over what lies beneath rather than added like the glows, since added light washes out to white on the pale floor, right after the glows and under a fizzle's pieces. The look, and every number below, was chosen on a mixer page that draws the real chambers with the game's renderer (https://claude.ai/artifact/NheohqT6ZoLXPRXy8SC1Gc, option C, Updraft).

- **Shafts:** about 6 at once on each portal, each lasting 0.48 to 0.78 s and fading in and out (the sine of how far through it is, to the power 1.5), at 0.8 of the particles' strength at most. Each is 0.15 to 0.35 of a tile wide and reaches 0.28 to 0.5 of a tile into the room, growing from 85 % of its length to all of it, and stands anywhere along the middle 78 % of the oval, its foot a little below the oval's middle. Across, it is a bell of light, its middle a little lighter than its sides; up, it is brightest just above its foot and thins out towards its top.
- **Sparks:** 20 a second on each portal, 0.009 to 0.0165 of a tile in radius, a pale middle (the lit inner edge's colour) in a ring of the portal's colour. Each leaves the middle 80 % of the oval and climbs 0.18 to 0.5 of a tile in 1 to 1.6 s, slowing a little, fading in quickly and out over the second half of its climb, and twinkles 2.5 to 4.5 times a second between full strength and a tenth of it. At the chamber screen's tile sizes on a screen of pixel ratio 1 they are only 1 to 2 px across, so they show mostly on denser screens.
- **Strength:** 0.65 at most, painted over.
- **Opening and closing:** a portal that just opened comes up to full strength over 0.3 s; when it closes, moves or breaks up, its particles still in the air fade out where they are in 0.2 s. A portal found already open, such as one opened while motion was reduced, gives off particles at full strength at once. Every step that opens, moves or closes a portal, each leg of a slide included, starts the new portal's particles rising and the old one's fading, and loading or restarting the chamber clears them all.

Each particle's place is worked out every frame from when it was born and numbers of its own, so nothing is kept per particle and the same moment always looks the same. The level already draws every frame while a portal glows, so the particles add only their own drawing (`docs/performance.md`). With reduced motion, and in the home menu's map and the gallery, no particles rise.

## Fizzler field

A fizzler's field is drawn by the game in code from no sprite (`src/game/fizzler_field.ts`), in the palette's colours: a see-through blue sheet across its gap, from one connector to the other, over the subject and every other element and under the glows, with thin wisps of cyan light winding slowly through it, light pooling along each connector in unsteady tongues, and short bright dashes drifting along it. Fizzlers side by side across one gap make one field, from the connector at one end of the run to the one at the other; the field spans its gap as the rules' `gapSpan()` says, left to right or top to bottom. The look, and every number below, was chosen on a mixer page that draws the real chambers with the game's renderer (https://claude.ai/artifact/3wkLx7rfPXjLhmPg9ps7qE, option F, Charged, with its glow at the connectors at 0.5, its wisps at 0.4 and 1 tile, and switching by fading in 0.7 s).

- **Sheet:** the field's blue, 50 % opaque over the whole tile.
- **Wisps:** two layers of thin winding filaments, from one seamless 128 px tile made once in code (three octaves of seamless noise, warped a little, kept only along their ridges), cyan, palest where strongest. One repeat spans a tile in the first layer and 1.37 tiles in the second; they drift diagonally the opposite ways, 0.07 and 0.095 of a tile a second along the field and across it, and breathe between 75 % and full strength every 7 and 5 s, at 0.32 and 0.22 at most.
- **Light at the connectors:** a steady glow reaching 0.3 of a tile into the field, palest at the plate, and over it six tongues of light along each connector, each 0.16 to 0.3 of a tile wide and 0.27 to 0.56 long, growing and shrinking every 2.5 to 5.5 s and flickering a little 1.4 to 3 times a second, at half strength.
- **Dashes:** 10 a tile along the run, each 0.04 to 0.1 of a tile long and 0.06 thick (3 px at least), a pale streak in a cyan glow, drifting one way or the other along the run at 0.03 to 0.09 of a tile a second and twinkling 0.4 to 1.8 times a second. One drifting out at one end of the run comes back in at the other, faded out within 0.08 of a tile of each end, so the jump never shows.
- **Flash:** whenever a step reports `fizzled` (the subject walked or crossed into a field that is on, or one switched on under it), its whole run brightens, cyan at 28 % fading fast, and a ring spreads from the middle of the subject's tile, from 0.06 to 0.81 of a tile at a near even pace, its pale line thinning, all gone in 0.6 s, so it stays inside a single field tile for most of its life. On a slide it flashes as the subject reaches the field's tile. Flashes run alongside each other, and loading or restarting the chamber clears them (`src/game/fizzler_flashes.ts`).
- **Splash:** when a portal shot a field that is on stops is refused, the field splashes over 0.55 s from the point the shot met: the middle of the fizzler's tile along the run, on the face the shot met, or, for a shot along the run from open floor at its end, the end of the tile it met, in the middle across. It lights up round that point, cyan at 70 % reaching 0.97 of a tile; a white spot reaching 0.3 of a tile flashes there at 90 %, gone in 0.12 s; and a ring spreads from it to 0.85 of a tile, quickly at first, a pale line halfway to white over a wider cyan glow, both thinning. All of it fades as (1 − progress)^1.6 and is as faint as the field is at that moment. Splashes run alongside each other, so two quick shots both show, and loading or restarting the chamber clears them (`src/game/fizzler_splashes.ts`). The miss ripple (see [miss](#miss)) plays as well, in the portal's colour. The look was chosen on a mixer page that draws the real chambers with the game's renderer (https://claude.ai/artifact/1tGYYaHyuBfQfPncg67YVJ, option B, Splash, at strength 1, 0.55 s, reaching 0.8 of a tile, brightening at 0.7).
- **Switching:** a field switching off or on fades out or in over 0.7 s at an even pace, every part of it alike, the connectors' lit slot fading with it; one switched back part way turns back from where it is.

Each tile is drawn straight onto the canvas, clipped to the tile, and everything on it is worked out from the moment drawn and numbers of its own, so the same moment always looks the same. While a field is on, the level draws every frame, as it does while a laser glows (`docs/performance.md`). With reduced motion, and in the home menu's map and the gallery, a field holds still at one moment of its motion and nothing flashes or splashes; switched, it appears or vanishes at once.

## Light barrier band

A light barrier's band is drawn by the game in code from no sprite (`src/game/light_barrier_band.ts`), in the palette's colours, among the blockers: over the floor and under the end plates (`light_barrier_end_*`), the boxes, the subject and the rays, a see-through band of teal hard light across the middle of each tile, from one end plate to the other, so it reads as a surface of light rather than a laser's thin beam or an emitter's ray. Light barriers side by side running one way make one band, from the plate at one end of the run to the one at the other. It is light, not a solid block, so it casts no shadow. One that is off isn't drawn; its plates are. The look, and every number below, was chosen on a mixer page that draws the real chambers with the game's renderer (https://claude.ai/artifact/GCjpKwFaXZePCNppt6sJRm, round 2, option C, Hard light: its lines across and its core line set to nothing, so not drawn).

- **Band:** 96 px of 256 wide (`BAND_HALF_WIDTH`, which the ray's end and a missed shot's ripple read), teal at 70 % over a deep teal rim 2 px wider each side at 50 %.
- **Edges:** along each edge a pale light fading inwards over a fifth of the band's width, and a bright edge line 3 px of 256 thick (1 px at least). They flicker faintly together, three waves at 7.3, 11.9 and 3.1 times a second averaged, losing up to 22.5 % of their brightness, each run at a point of its own.
- **Light at the plates:** where the band leaves each end plate of its run, light pools in it at full strength, palest at the plate and gone 0.4 of a tile in.
- **Switching:** a band switching on unfolds over 0.3 s at an even pace: a bright white line runs out of both plates along the band's middle and meets in the middle by 35 % of the way, a bright front leading each half, then widens into the band from 30 %; the plates' slots are lit by a quarter of the way. Switching off is the same backwards, so the slots stay lit until the last quarter. One switched back part way turns back from where it is.
- **Reaction:** when a portal shot the band stops is refused, and when the subject walks into a band that is on (a move, or a turn the way it already faces, that leaves it on its tile though its own tile lets it go that way; the rules report nothing for it), the band reacts over 0.7 s, at 80 % strength: it brightens round where it was met, on the face met, the face flares there, and a bright bar across the band splits in two and runs off both ways along the run, 1.3 tiles by the end, fading. A shot met along the band, from inside a band tile, reacts at the end of the tile it met. A band tile still reacting takes no new reaction, so a key held into it pulses, while other tiles, of the same band or another, react alongside it; loading or restarting the chamber clears every reaction (`src/game/light_barrier_reactions.ts`). A shot keeps the miss ripple (see [miss](#miss)) in its portal's colour as well; a slide that stops in front of a band doesn't react.

A steady band's tile is drawn from two images painted once per tile size (its body, then its edges as bright as they flicker); one switching is painted straight onto the canvas, clipped to the tile. While a light barrier is on, the level draws every frame, as it does while a fizzler's field is on (`docs/performance.md`). With reduced motion, and in the home menu's map and the gallery, the edges hold steady at full brightness and nothing reacts; switched, a band appears or vanishes at once.

## Fizzle

When the subject fizzles (it walks or crosses into a fizzler that is on, or one turns on under it), each portal it loses breaks up, and so does a portal on a wall side facing a fizzler that switches on (a box flies home instead, or, one a link reaches, breaks up the same way, see [fly home](#fly-home)): the game cuts the sprite, as last drawn, into small square pieces, 9 across a tile, which round off into dots as they drift a short way out from its middle (0.15 of the sprite's side on average, 0.2 at most), shrink and fade in about 0.6 s, over everything but a box's pieces flying home and a missed shot's ripple. There is nothing extra to draw, but the pieces show the sprite's own pixels, so a portal drawn as a thin outline breaks into very few. A step that reports `fizzled` or `portalFizzled` starts it (`src/game/fizzle_particles.ts`), breaking up each portal open before the step and closed after it; with `portalFizzled` alone, only one whose wall side faces a fizzler that is on after the step, so a portal a blocked wall closes in the same step still just vanishes. A new break-up replaces pieces still drifting, unless it breaks nothing up, or it is a later part of the same slide, whose pieces join them, and loading or restarting the chamber clears them. A fizzler switching off or on fades its field out or in (see [fizzler field](#fizzler-field)). With reduced motion, and in the home menu's map and the gallery, nothing breaks up.

## Fall

When a ditch opens under a box lying on it, or under a box the subject has just put down on it, and the ditch is still open once the step ends, the game draws the box falling into the pit (a box sent back to a button that bridges the ditch again flies home instead, see [fly home](#fly-home)), from its own sprite, so there is nothing extra to draw. It hangs where it was for a moment while the grate starts to slide away, then drops ever faster, shrinking towards the middle of the pit to a quarter of its size and fading into the dark, in about 0.45 s, without a shadow and inside its tile: over the ditch and its sliding grate, under everything standing on the floor. A step that reports `boxDestroyed` starts it for each box a ditch destroyed (found by `findDestroyedBoxes` in `src/game/destroyed_boxes.ts`, drawn by `src/game/box_fall.ts`), replacing a fall still running unless it drops nothing, and loading or restarting the chamber clears it. Meanwhile it gathers at its start (see [fly home](#fly-home)), unless a link reaches it: then it is gone, absent until a link brings it in. With reduced motion, and in the home menu's map and the gallery, nothing falls.

## Fly home

When a box goes back to its start tile (destroyed where a door closes or a laser, a light barrier or a fizzler switches on, destroyed in the subject's hands when it fizzles, or sent home by a link: a button, a switch or a receiver), the game draws it coming apart where it was and flying home, from its own sprite, so there is nothing extra to draw: cut, as the break-up cuts it, into small square pieces, 9 across a tile (the box as `box`, or `box_mirror` with its mirror the right way round in the room; at the size and place of the box `subject_holding_box` shows in its hands when it was carried into a fizzle), which round off and drift a short way out, then set off one after another along slight bows to their own places in the box at its start, shrinking a little in flight and growing back and squaring off as they land, all within about 0.8 s, whatever the distance, over everything but a missed shot's ripple. The box's shadow forms at its start as the pieces land, and the box rests whole once they have. A box that falls into a ditch (see [fall](#fall)) gathers at its start instead, its pieces coming in from about half a tile around it, growing and squaring off as they land, in about 0.48 s, while its shadow forms, and so does a box a link brings in, which was nowhere before; nothing marks where a box that starts absent will appear. A box picked up again before it lands is drawn as it is. A step that reports `boxDestroyed`, `carriedBoxDestroyed` (a box carried into a fizzler that is on), `boxSentBack` (a link sent a box home) or `boxAppeared` (a link brought in a box that started absent) starts it for each box that went back to its start: every box destroyed where it lay, the one carried, every box brought in, and every other box that went from elsewhere to its start (found by `findReturnedBoxes` in `src/game/returned_boxes.ts`, drawn by `src/game/box_returns.ts`). It runs alongside the boxes still on their way, a box sent home again starts over, and loading or restarting the chamber clears them all. A box a link reaches, destroyed anywhere but on a ditch, goes nowhere (`docs/elements.md`, "A destroyed box a link reaches"): it breaks up where it was, as a fizzled portal does (see [fizzle](#fizzle)), its pieces rounding off into dots as they drift a short way out, shrink and fade in about 0.6 s, over everything but a missed shot's ripple, at the size and place it was drawn (in the subject's hands, for one carried into a fizzle, or where it lay, for one picked up from inside a fizzler that is on), and nothing marks its start; one that falls into a ditch only falls. A link that brings it in before its pieces have faded ends them, and it gathers at its start. With reduced motion, and in the home menu's map and the gallery, a box is simply back at its start, or simply there, or simply gone.

## Miss

When a portal shot misses, the game draws a ripple in the shot's colour where it stopped, over everything, from no sprite: the face the shot met lights up as a line 0.84 of a tile long and 0.05 wide across the shot, fading in about 0.28 s, and two thin half rings, 90 ms apart, spread back towards the subject, from 0.2 to 0.8 of a tile along the face and up to 0.28 of a tile back, thinning and fading in about 0.42 s each, so all of it stays within the tile's width and is gone in about 0.52 s. It sits where a portal would have opened on a wall, 0.125 of a tile in; 0.06 of a tile into a door or the exit, at its near edge; on a fizzler's field's edge, the side of its tile the shot met, since the field fills the tile, where the field splashes too (see [fizzler field](#fizzler-field)); on the near face of a light barrier's band when the band runs across the shot, or 0.06 of a tile into its tile, as at a door, when it runs along it, where the band reacts too (see [light barrier band](#light-barrier-band)); and, for a shot that left the chamber through an open door or exit in its edge, just inside the doorway. A shot from inside a fizzler that is on does nothing, so draws nothing. The ripple starts where the rules' `shotStop` says a refused portal shot stopped (`src/game/miss_ripple.ts`), replacing a ripple still spreading, and loading or restarting the chamber clears it. A refused crossing or interact shows none, and a shot tried while carrying a box never leaves, so it shows none, and no field splashes or band reacts for it. With reduced motion, and in the home menu's map and the gallery, nothing ripples.

## Antlines

An antline is a dotted line on the floor from a button, switch or receiver to one element it links, as in the original game, drawn by the game in code from no sprite along the corners the chamber file gives (see `docs/elements.md`). Its dots, 3 per tile, one on each tile's middle, so each corner gets one, are 0.15 of a tile wide, each with a border 0.025 of a tile wide (never thinner than a pixel) drawn inside its edge, in its colour 30 % darker. It runs from the middle of the button's or switch's tile, whose sprite hides its start, or of the receiver's, whose wall hides it up to the floor, to the edge of the element's tile, its last dot 1/6 of a tile before it, the same whether the element is drawn or not. It lies over the floor and under everything else, so the floor marks, the walls with their shadow and every element hide it where it runs under them, and it shows again beyond, though over a plain wall, or a blocked wall no link reaches, dots of its own are drawn on the wall's top (below). It is cyan while unlit, and amber, lit, while the button, switch or receiver it starts on is active: a button held down, a switch used, a receiver lit, whatever the element it leads to does, a line to a box included, so the unlit lines to an element several of them link show which are still to be made active. Unlit lines are drawn first, lit ones over them. The colour changes at once with the step, with no fade, so reduced motion changes nothing; the home menu's map and the gallery show them too.

Where the line crosses a plain wall, or a blocked wall no link reaches, the game draws its dots on the wall's top too, into the backdrop right after the walls and their shadow, both when the backdrop is first drawn and when an antline lighting up or going dark draws it again: on each such tile along it but its first and its last (the button's, switch's or receiver's, and the element's), over the steel just as over a plain wall, since both are drawn in the backdrop and never change, and over a blocked wall no link reaches that starts unblocked, drawn as a wall. A blocked wall a link reaches, an emitter or a receiver still hides it: a linked blocked wall's steel is painted over the line among the blockers while it is blocked and slides away when it opens, so dots on it would show only while it takes portals, and the chamber loader rejects a line that runs through one rather than ending on it (`docs/elements.md`). Its dots there are the floor's, in size, colours and border, unlit lines first and lit ones over them, placed to keep clear of the wall's bevels. Each end of the tile along the line is bevelled when the tile beyond it is outside the chamber or isn't part of the mass of walls (walls, blocked walls, emitters and receivers), the same test the [joins](#joins) use, so it matches the bevels drawn. Where the line runs straight across the tile with walls at both ends, it takes 3 dots, as on the floor: the middle, and a third of a tile either side. Where it runs straight and either end is bevelled, it takes 2, a third and two thirds of the way across, centred on the tile and clear of the bevel, so a wall one tile thick shows 2, half a tile from the floor's dots on each side instead of a third. Where it turns on the tile, it takes the middle dot and each arm's dot a third of a tile out, as on the floor, but for an arm whose end is bevelled, whose dot is drawn in to 0.225 of a tile from the middle, its edge just meeting the bevel's lit lip, so it stays on the flat top, whole, and a turn on a wall tile beside the floor still shows the way the line leaves it, into the button, switch, receiver or element beside it. (Chosen 2026-11-23 over a dot left straddling the bevel, folded over it, lying on it or shaded on it: https://claude.ai/artifact/SyhyrRz4EbTWzgzYNxehSx.) The home menu's map and the gallery show these dots too.

## Rays

An emitter's ray is drawn by the game in code, from no sprite, from the rays as they run in the state shown (`src/game/ray_drawing.ts`), shaped like `laser_on`'s beam but recoloured pale gold (see [look](#look)) and narrower, a 23 px beam of 256 against the laser's 30. Each straight run is filled with three bands, each a gradient across it, every ray's haze first, then every soft edge, then every beam, so crossing rays layer cleanly: a haze tinting the floor, about 0.29 of a tile wide; a soft edge in the rim's colour at 80 %, about 0.1 wide; and the beam, about 0.09 wide, from the dark rim through the body to the white-hot core. Each band is at least 1.2 canvas pixels wide, so a ray still shows on the home menu's map. Its glow is the laser glow's bell, about 0.48 of a tile wide (see [glow](#glow)).

A ray starts at its emitter's face and ends at the face it meets of a wall, a receiver, a closed door or the closed exit; at a portal, at the wall's face, meeting the oval's near rim without painting over it, starting again at the other portal's face; at the middle of the subject's or a plain box's tile, which stand over its end; at a light barrier whose band runs across it, at the band's near rim, 50 px of 256 short of the tile's middle (its face, 48 px out, and its rim, 2 px more, which the ray drawing reads from `src/game/light_barrier_band.ts`; the miss ripple sits on the face itself), or at the tile's edge when the band runs along it. It turns at a mirror box's middle, the corner hidden under the box. A ray changes at once with the step that cuts or frees it, with its emitter's lens, while a receiver's eye fades over about 0.25 s; the home menu's map and the gallery draw rays too.

## Exit shadow

The exit's tile is shaded by the game in code, from no sprite, so the open exit reads as the way out of the chamber, into the dark, and never as an open door: black, as opaque as the square of how far across the tile it lies, clear at the tile's inner edge and fully black at its outer edge, on the chamber's edge, so it stays light over most of the tile and darkens fast near the edge. It is painted with the floor, over its surface detail and under the antlines (which stop short of the exit's tile), the walls and their shadow, and the same in every state: the closed exit's opaque `exit_closed` hides it, and it shows between the leaves as they slide. Only an exit in one outer wall, away from the corners, has one, which the chamber check requires of every chamber. The home menu's map and the gallery show it too; nothing about it moves, so reduced motion changes nothing. The subject on the exit, which it only reaches as the chamber is completed, is drawn under it too, so it darkens as it walks out (see [the subject](#the-subject)).

On the chamber screen the exit is see-through instead, so it runs into the dark stage around the chamber with no step where they meet: the same fade, by the same amounts, cuts the whole backdrop out across the exit's tile once the walls and their shadow are drawn, so the stage behind the canvas shows through, clear at the tile's inner edge and fully at its outer edge. The canvas there has no border, the renderer clears it before each frame, and the subject walking out fades out with the floor instead of darkening. The closed exit and its sliding leaves are drawn over it as ever. The home menu's map and the gallery keep the black shadow, since a light wall lies behind the map.

## Sliding

When a door or the exit opens or closes, it slides over about 0.3 s: the game draws `door_closed` (or `exit_closed`) cut down its middle over the floor (and, for the exit, its shadow), each half slid out to its side and cut off at the tile's edge, as if going into the wall, until nothing is left. So the closed sprite's two leaves must meet on the tile's middle line.

A blocked wall a link reaches slides the same way when it is switched, over about 0.3 s: its `blocked_wall` tile, joined as it is drawn, is cut down its middle over the wall beneath it, each half slid into the wall beside it, along the run of walls it lies in (up and down when more walls lie above and below it than left and right), until only the wall is left, and back when it is blocked again.

A ditch switched slides its grate over about 0.3 s: the ditch is drawn as part of the pit, and `ditch_bridged`, whole, slides in over it from one side, cut off at the tile's edge, as if coming out from under the floor, or back out the same way. It never comes from another ditch unless ditches lie on all four sides: in a row of ditches running left to right it comes from above (from below when a ditch lies above), and otherwise from the left (from the right when a ditch lies left). A ditch switched alone among open ditches stays part of their pit while it changes, so their rims beside it go as soon as it starts to open and appear only once its grate is fully in.

There is nothing extra to draw. With reduced motion, and in the home menu's map and the gallery, nothing slides.

## Turning arrows

When a link turns an arrow, its `turntable_arrow` rotates the quarter turn about the tile's middle over about 0.3 s, eased out like the doors, from where it is drawn if it was still turning; its `turntable` stays. A subject standing on it turns with it on its own clock, as it does for any change of facing (see [the subject](#the-subject)). There is nothing extra to draw. With reduced motion, and in the home menu's map and the gallery, nothing turns: the chevron is drawn at the way the arrow points.

## Steps

A step that changes the state is drawn over a few frames, from the state before it to the state after it (`src/game/step_animation.ts`), so there is nothing extra to draw. It takes about 120 ms, eased out and started one frame back, so the frame of the key press already shows part of it. A slide follows its path at one tile every 60 ms, a portal crossing counting as two, its last tile eased out, so a six-tile slide takes about 0.42 s. Its last frame is drawn exactly as the state after it.

Only a rules step that changes the state starts this drawing. Every key press the game takes ends the step being drawn at once, even a press that changes nothing, so a new key never waits. A load and a reset show their state at once, dropping the step being drawn, and a load or a resize redraws at the latest frame's time, so a step being drawn never goes back. None of the other animations and effects (the subject's turn, the elements switching, the portals' opening and particles, the break-ups, the boxes' fall and flight home, a missed shot's ripple, the fizzlers' flashes and splashes and the light barriers' reactions) holds up a key press either.

The level redraws when the state changes; every frame, paused or not, while a step is being drawn (its glide, a slide along its path or a walk-out past the exit), until a frame draws its end; and every frame while anything else on the canvas moves (a ray's glow, held steady, doesn't), then once more when that stops. Otherwise idle frames draw nothing.

Part way through a step, the subject and a box it carries are drawn where its pose puts them (`src/game/subject_pose.ts`): a move glides it one tile; a portal crossing slides it into the entry portal, facing it, then out of the exit one, each half clipped to its tile; and a slide goes the same ways, leg by leg, along its path. Everything else shows the state after the step at once, but for the effects above, the elements the step switched (below), the subject's turn (see [the subject](#the-subject)) and a slide.

Drawing a step over time holds back nothing else: the sounds, the move and portal counters, the log of actions and the completion (`onCompleted`, which opens the completion dialog and pauses the game) stay in the frame that takes the key press, and the clock is unaffected. A slide is the exception. Its counters and its log stay at the key press, but what happened on each tile it entered (its sounds, a fizzle's break-up) waits until the subject is half way into that tile, or through the portal onto it, and its stop and settling (buttons, doors, the elements switching, the completion) until the slide ends, but for reaching the exit, heard with the last tile. Until then everything but the subject is drawn as the state on the last tile it has reached, and as the state before the step until it reaches the first (`shownState` in `src/game/step_animation.ts`). A key press first plays all that a slide still has waiting; a load or a reset drops it.

When a step completes the chamber with the subject arriving on the exit the way out of its outer wall, the subject walks out: with no easing, a move at 180 ms a tile and a slide at its own pace, across the exit and on until it is a whole tile past the chamber's edge, where it is held. It is drawn unclipped until the chamber's edge cuts it off, the distance still to go rounded to whole canvas pixels, with the exit's shadow laid over it (see [the subject](#the-subject)). The clock stops at the key press that completes the chamber, though the completion may wait for a slide and waits for a walk-out to end, everything else staying at the key press but what a slide's stop sets off.

Every element a step switches changes over a short time, from where it is drawn if it was still changing (`src/game/element_transitions.ts`, which compares each receiver's lit flag as it compares the blocked flags): an arrow a link turns (see [turning arrows](#turning-arrows)), a blocked wall, a ditch, a door and the exit (see [sliding](#sliding)), a fizzler's field (see [fizzler field](#fizzler-field)), a light barrier's band (see [light barrier band](#light-barrier-band)), and a laser and a receiver's eye, which fade over about 0.25 s (see [the set](#the-set)); a ray and an emitter's lens change at once. No key press waits for one or cuts it short, and loading or restarting the chamber clears them.

With reduced motion (`prefers-reduced-motion`, read each time something could be drawn over time), nothing is drawn over time: a step and every element it switches are drawn at once, the glows, the fizzlers' fields and the light barriers' edges hold still, no animation or effect plays, only changes are drawn, and the subject stays on the exit.

## The subject

The subject's two sprites are the only ones not drawn in code. They are painted images that break this spec on purpose: their light is painted, not straight overhead; the subject wears orange and its portal gun glows blue, the portals' colours; and their sources are the painted PNGs `art/sprites/subject_holding_gun.png` and `art/sprites/subject_holding_box.png` (1526 × 1526 px each), with no SVG.

Each is one still image: the subject glides from tile to tile and through portals, with no walking frames (see [steps](#steps)). Reaching the exit, it glides on out past the chamber's edge, drawn on a layer of its own with the exit's shadow laid over it, so it darkens across the exit (on the chamber screen, fades out into the stage) and is cut off at the canvas's edge (see [exit shadow](#exit-shadow)). It holds its portal gun while its hands are free and a box, with no gun, while it carries one, the game swapping the sprite as it picks the box up or puts it down.

Whenever the way the subject is drawn facing changes (a turn in place, a move another way, a walk into a wall, into a portal and along a slide, turning with the arrow it stands on), it turns there on a clock of its own (`src/game/subject_turn.ts`), from the angle drawn, the shorter way round (a half turn clockwise), over about 0.1 s a quarter turn and 0.15 s a half, eased out and started one frame back, its shadow and a carried box turning with it. A key press never cuts a turn short: the next turn carries on from the angle drawn. Coming out of a portal, or when a key press ends a crossing before the subject came out, it faces its new way at once, as it does with reduced motion; loading or restarting the chamber clears the turn.

Both are exported the same way, so the figure keeps its size and its head stays in place when they swap: centred as painted, padded to a 1648 px square so the figure stands 238 px tall in the 256 px tile, cleared of faint stray pixels (alpha under 3 %) and shrunk to the tile. The portal gun, or the box held out, makes the painting top-heavy, so the subject turns about a point on its head, a little above the head's middle. The painted box sits 0.26 of a tile ahead of the tile's middle, 0.7 of a tile across (`CARRIED_BOX_AHEAD` and `CARRIED_BOX_SIZE` in `src/game/renderer.ts`): the game lays a carried box's look there, marks a carried mirror box's mirror there, and draws the box's own sprite there when it breaks up in the subject's hands, carried into a fizzle (`box`, or `box_mirror` with its mirror the right way round in the room), so repaint the box there or change those two. A falling box is drawn on its own tile, at full size (see [fall](#fall)).

A carried box keeps its look of its own (see [element detail](#element-detail)), laid over the painted box's grey, never over the hands that hold it. The painted box is always plain, so the game marks a carried mirror box in code, from no sprite: its mirror's line, centred on the painted box, reaching 0.13 of a tile from its middle each way across and up or down, rising to the right for `/` and falling for `\`, the right way round in the room whichever way the subject faces. It is three round-capped strokes, each at least a pixel wide, bottom to top: the frame, dark grey (44, 48, 54), 0.07 of a tile wide; the glass, pale grey (226, 231, 238), 0.045 wide; and a white glint, 0.012 wide. It is drawn right after the subject's sprite, so it glides with it and is clipped with it through a crossing.

To export them again, from the project's root:

```sh
convert art/sprites/subject_holding_gun.png -channel A -level 3%,98% +channel -background none -gravity center -extent 1648x1648 -resize 256x256 -quality 90 -define webp:alpha-quality=100 src/assets/images/chamber/subject_holding_gun.webp
convert art/sprites/subject_holding_box.png -channel A -level 3%,98% +channel -background none -gravity center -extent 1648x1648 -resize 256x256 -quality 90 -define webp:alpha-quality=100 src/assets/images/chamber/subject_holding_box.webp
```

## Not in the set yet

- **Decorations** not tied to the rules, such as lights along the outer wall and hazard stripes at wall ends. Wear on the floor and the walls is drawn in code, from no sprite (see [surface detail](#surface-detail)), and each element's look of its own over its sprites (see [element detail](#element-detail)).

## Trying a sprite

Drop the file into the folder, and `npm run dev` picks it up. The sprite gallery, at `/src/dev/sprite_gallery.html` in `npm run dev`, reloads by itself when a file lands and shows:

- each sprite as the game has it, at full size on a checkerboard, with its size and whether its file is in use, missing, not downloaded or refused (and why); one without a usable file shows as an empty frame, since the game draws nothing for it;
- a small chamber with every element and an antline, drawn by the game with everything on and with everything off (the antline unlit, then lit; the turnable arrow pointing its own way, then turned; the emitter on, its ray turned by a mirror box onto the receiver, lit, then the emitter off and the receiver dark), the subject carrying a box and both portals open;
- every way walls and open ditches meet;
- each chamber at its start, every campaign chamber in play order, then Playground 1 to 12.

The small chamber and the walls and ditches come at the smallest tile the home menu's map draws (a playground chamber's map included), then at 40, 100 and 230 px, and each chamber at 40 px, each canvas pixel on one screen pixel.
